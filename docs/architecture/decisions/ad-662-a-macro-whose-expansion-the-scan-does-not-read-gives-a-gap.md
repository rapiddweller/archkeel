# AD-662 A macro whose expansion the scan does not read gives a gap

**Status.** Accepted (owner order: fix the false PASS). Part of #880, closes #1371 and #1374. It amends AD-516, AD-614 and AD-656.

**Reason.** The scan reads the body of each `macro_rules!` of the workspace. It reads no other expansion: a procedural macro, a `macro_rules!` of a crate outside the scan, or a macro that an import binds. A call of such a macro gave no gap when its tokens held no path, so `mac::call_d!()` in `a`, which writes `crate::d::f()`, left `a -> d` PASS. rustc resolves a `crate::` path of a `macro_rules!` body in the crate of the call, so a registry `macro_rules!` can do the same. An expansion can also write an `impl` anywhere, even in a block. That impl applies in the whole crate, so other modules can run it without naming the module of the call.

**Decision.**
1. A call of a macro that no `macro_rules!` of the workspace defines, and that AD-614 does not carry from another crate, gives a gap with the module of the call as its source and an unseen target, as an attribute macro does. This also holds for a plain name in a workspace body that no workspace macro defines, because rustc resolves it at the place of the call.
2. The module of such a call may hold an impl that the scan does not see. Each module that may reach it (its crate, and each crate that depends on it) gets a pair gap to it, by the AD-516 rule. The same holds for a `macro_rules!` call whose expansion writes a trait impl that is not anchored, holds a path call or a macro definition, or whose call tokens hold an `impl`. A member of an inherent impl is reached only by its name: a method call or a path `S::m` of a member that a macro may define outside the file of its type gets the AD-656 pair gap, and a `const` is a member name as a `fn` is.
3. AD-656 anchors amended (#1374): a call expands one arm, so only a type of the same arm anchors an impl. A struct, enum or trait of the module anchors only when every configuration has it (no `cfg` or other non-inert attribute), because a `use` may bind the name when `cfg` removes the item.
4. `macro_identity.rs` proves two kinds of call. Their tokens are read as code, and they give no gap:
   - A macro of `std`, `core` or `alloc` from a fixed table, called by its plain name with the prelude, or by a `std`, `core` or `alloc` path. The plain name is proved when no `use` binds it, no `macro_rules!` of the crate has the name, no `extern crate` is above the module, and each glob is proved by the derive namespace proof (AD-535). A function of the name is in another namespace.
   - A reviewed registry `macro_rules!` at its locked version, through the dependency of the crate, as for a derive (L-117): `serde_json` 1.0.154 `json` and `schemars` 1.2.3 `json_schema`. Their arms write only `$crate` and `::core` paths and the call tokens.
5. A call in the tokens of another macro keeps its own path, so the proof reads it.

**Why it is sound.** A call outside the table writes code that the scan does not see, and both its own module and each module that can run an impl from it get a gap. A table macro writes paths of its own crate and the call tokens, which the scan reads. An `impl` in the tokens withholds the proof.

**Own code.** The native workspace calls `json!`, `json_schema!` and `syn::Token!`. The first two are proved. The lock holds two `syn` versions, so the unique registry identity of L-117 does not hold for `syn`. The five `Token![,]` and `Token![=]` uses now name `syn::token::Comma` and `syn::token::Eq`. The `with` arm of `section_facts!` wrote `impl $name { fn data }` and got `$name` from a call of its other arm, which item 3 does not anchor: it now writes `impl CommonData for $name`, a trait of `facts::sections`, the module of each call. Self-check: 86 PASS and 0 gaps before and after; without these two changes 22 rules were UNKNOWN. One false gap fixed in passing: `requirement_tests.rs` declared `PythonPhase` in two fn bodies, and the oracle read the name as a possible module. It now has one `use` at module level, the remedy that the limits page names.

**Rejected.** The derive prelude proof as it is: it refuses a name that any namespace declares, so a function `matches` or `write` withheld the `std` macro. A module gap without a source: the Rust oracle allows only pair-scoped gaps of an unseen expansion. `syn` in the table while two versions are locked.

**Tests.** `tests/test_collector_false_pass_rust_unread_macro.py` (rustc accepts each plant and rejects `a.rs` without `mod d;`; 11 of the 12 gap plants are a false PASS without the gaps; 2 std twins keep PASS), `tests/test_collector_false_pass_rust_macro_method.py` (#1374, a `cfg`-removed anchor, a macro `const`), the macro orphan of `tests/test_collector_false_pass_rust_orphan_impl.py` (an open form before), `macro_identity_tests.rs`, `collect_tests.rs`, `symbols_tests.rs`. Each new plant is a false PASS on main `b66769c82`, except the `impl` passed through call tokens.
